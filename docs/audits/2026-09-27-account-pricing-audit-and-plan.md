审计日期：2026-09-27。范围：PartsPro-V4 / `yiuxrjqexlfjtxxrkqvi` 的只读价格、客户分类汇总、定价函数，以及当前工作区的目录、购物车、结算和等级代码。未修改业务代码、账号、价格或生产数据库，未发布。本文是审计交付物，不替代 `docs/roadmap.md` 的项目状态。

## 1. €1.90 / €1.40 的解释

截图商品是 **REMAX Cavo USB-C/USB-C 65W 1,2 m CB25 – Arancione**，SKU `REMAX-6954851225270`。

生产数据库当前：批发原价 €1.40，零售原价 €1.90。生产 `private.resolve_customer_product_price` 明确让 REMAX 跳过客户专属价、等级减额和价格组折扣，但仍按客户 `customer_type` 选择零售或批发原价。免折扣不等于两类客户同价。

| 截图商品 | 生产批发原价 | 生产零售原价 | 截图 |
| --- | ---: | ---: | ---: |
| CB25 240W 黑色 | €1.80 | €2.40 | €1.80 |
| CB19 65W 蓝色 | €2.20 | €2.90 | €2.20 |
| CB25 65W 橙色 | €1.40 | €1.90 | €1.40 |
| CB16 65W 橙色 | €1.60 | €2.10 | €1.60 |

这组价格与批发价完全吻合。未提供两个账号的客户编号，故尚不能确认某个具体客户是否被错误分配类型，也未以两个真实登录会话复现。当前证据足以解释价差机制，不足以把某个账号的分配定性为操作错误。不能仅因差价把所有客户改为批发或把两套原价合并。

生产 migration history 已确认包含 `20260916205954`（保护膜）、`20260925131412`（REMAX 免折扣）、`20260926091650`（REMAX 价格取整）。这不是仅存在于本地的免折扣规则。

## 2. 当前价格制度

1. 账号身份与客户交易档案分开；员工可有自购档案，代客下单使用被服务客户的档案。
2. 客户 `retail / wholesale` 决定基础价；等级不是零售/批发身份。
3. REMAX / `Pellicole Protettive`：保留所选基础价，全部折扣跳过。
4. 普通商品：批发客户存在有效数量协议价时优先采用协议价；否则基础价减等级固定金额，再乘批发价格组折扣。
5. 最后执行现有成本保护逻辑，产生最终价、价格来源和版本。

| 等级 | 累计消费门槛 | 每件固定减额 |
| --- | ---: | ---: |
| Bronze | €0 | €0 |
| Silver | €1,000 | €0.25 |
| Gold | €10,800 | €0.50 |
| Emerald | €20,600 | €0.75 |
| Diamond | €30,400 | €1.00 |
| Master | €40,200 | €1.25 |
| King | €50,000 | €1.50 |

有效促销等级覆盖普通等级；现有新注册促销是 King 三个月。促销过期直接按累计消费回算。价格组定义有 0%、2%、4%，但本次查询中全部 18 个 active + assigned 档案的价格组均为空，客户商品协议价记录为 0。因此价格组和数量协议价不是本次 REMAX 差价原因。18 个档案含员工自购，不代表 18 个普通客户。

## 3. 问题清单

### F1 — P1：人工等级与促销过期规则冲突（生产已确认）

4 个 active + assigned 普通客户记录为 `level_source=manual`、`level=king`，但有效等级为 3 个 Bronze、1 个 Silver；另有 1 个暂停客户同类冲突。`customer_effective_level` 不接收 `level_source`，过期促销分支直接按消费计算，绕过人工等级。新人工设置接口会清掉促销，但历史混合数据仍存在。

证据：生产函数与聚合查询；`supabase/migrations/20260620140151_customer_effective_level_search_path.sql:20`；前端同样逻辑 `src/lib/partspro-pricing.ts` 的 `effectiveCustomerTier`。

影响：非免折扣商品会出现与人工授予等级不符的价格。需明确人工覆盖与促销优先级，列出受影响档案供核对，再受控修复；不得直接批量恢复 King 而不核对授予依据。

验收：人工永久/有期限、促销有效/过期、消费跨门槛组合，前后端有效等级一致。

### F2 — P1：价格服务失败后本地兜底规则不完整（代码确认，发生频率未知）

`src/lib/partspro-repository.ts:5797` 将 RPC 错误变成空数组，`:5716` 附近合并逻辑保留原行；`src/lib/partspro-account-context.ts:314` 可以用本地规则重算。该本地规则只有零售/批发与等级/免折扣，没有完整协议价、价格组、成本底线，也没有以实际代客档案作为独立参数。

影响：故障时可能显示不完整报价或价格不可用；若原行有基础价，则存在与数据库最终报价不一致的路径。下单服务端复核是保护，但无法消除页面误价。

修复：权威报价失败返回明确 unavailable，不能把本地估算标为可交易价格；统一报价 DTO、实际客户 ID、数量及版本。验收 RPC 超时、缺行、权限拒绝和代客模式，不产生可下单估算价。

### F3 — P1：数量协议价的预览与提交不一致（代码及生产目录 RPC 确认；当前未配置协议价）

`src/app/api/orders/preview/route.ts:227`、`src/app/api/orders/route.ts:353` 经仓库函数仅传 SKU；生产 `resolve_customer_catalog_prices` 按商品 MOQ 报价，最终下单却按实际数量解析。后续启用数量协议价时可能反复报价格变化。

修复：购物车、预览、下单统一传 `{sku, quantity}`；事务内保留最终重算。验收 MOQ=1、门槛10，数量9/10/11、合并同 SKU、预览后数量和规则变化。

### F4 — P2：5 个在售商品低于 15% 毛利目标（生产已确认）

现有公式 `least(base_price, round(cost_price / 0.85, 2))` 将保护价封顶于原价，因此原价本身不足时无法保证15%。证据：`supabase/migrations/20260925131412_exempt_remax_discounts_and_sync_arrival_state.sql:199`，生产同定义。

| SKU | 批发价 | 按商品成本计算的毛利率 |
| --- | ---: | ---: |
| 3000000311233 | €37 | 13.78% |
| 3000000353318 | €38 | 14.74% |
| 3000000411995 | €40 | 12.75% |
| 3000000411858 | €40 | 12.75% |
| 3000000365892 | €53 | 11.23% |

这些不是已证明的亏本商品，也未计入所有运营成本。若15%为强制底线，应在改价/导入时拦截或要求有期限的批准例外；不要在结算时悄悄涨价。严格底线的分位取整应向上，普通四舍五入可能略低于目标。

### F5 — P2：零售/批发价格倒挂（生产已确认）

SKU `3667075243373`，Galaxy A17 4G 带框 Incell 屏：零售价 €14、批发价 €15。需确认是否有意促销；没有批准例外则修正。改价、导入与批量调价增加倒挂校验及审计。

### F6 — P2：优惠标签可能大于实际减价（代码及候选数据确认）

`src/lib/partspro-price-display.ts:62` 优先展示理论等级固定减额；数据库触发成本底线后不相应改写该理论字段。当前商品中有4个满足“King减额被底线部分截断且仍有折扣”的条件。不是4笔已发生的错误交易。

修复：标签展示 `basePrice - finalPrice` 的实际优惠，另列理论等级权益与适用限制。验收有底线、叠加折扣、免折扣和零优惠。

### F7 — P2：价格类型缺少足够清晰的客户解释（UI 代码及截图确认）

`src/components/partspro/product-card.tsx:285` 显示价格及优惠，未直接解释当前零售/批发价表。后台类型与等级分开修改；员工转客户还显式重置为 retail + needs_review（`admin-accounts-panel.tsx:3329`）。这本身可以是安全默认值，但须明确提示重新分类，避免以为 King 自动获得批发价。

修复：账号页与目录显示当前价格类型、有效等级、有效期；管理员变更前展示代表 SKU 前后价、影响范围和原因。是否允许某个客户批发，需要业务资格与审计依据。

### F8 — P2：退款对累计消费的影响未闭环（口径风险）

生产 `private.recalculate_customer_level` 累计未取消且已付款订单的 `total_net`，未直接扣除售后钱包退款。代码退款流程见 `supabase/migrations/20260606093157_wallet_refund_approval_flow.sql:426`。如果制度定义的是退款后净消费，退款后仍保留升级贡献，钱包再次消费可能重复贡献；若明确采用历史购买额，则需将制度写清。

修复：统一商品消费、运费、取消、部分退款、缺货调价、钱包再次消费口径；按事件幂等更新，避免订单额已减又重复扣退款。验收部分/全额退款与等级门槛回退。

### F9 — P2：同页身份变化可能保留旧报价（代码风险，未真实会话复现）

`src/components/partspro/cart-page.tsx:193` 普通模式 key 为 default，`:210` state 从初始产品赋值，`:487` 只补缺失 SKU。`cart-sync-bridge.tsx:518` 认证事件同步购物车，却未同步清除页面报价缓存。

修复：缓存绑定实际客户、员工自购/代客模式和报价版本；身份变化清空并重取，数量变化重报价。验收两个账号同 SKU 不同价、跨标签身份切换、代客切换。

### F10 — P2：注册 King 活动缺少明确活动结束开关（生产规则确认）

生产 `apply_customer_signup_king_promo` 为符合条件的新客户从创建时间起授予三个月 King，没有活动总体开始/结束配置。可能是有意长期迎新政策，不能直接判定错误。需确认政策；建议用活动配置、适用人群、活动截止、单客户到期和成本模拟管理，避免一次活动永久运行。

## 4. 修复计划与制度闭环

主责：价格与客户部；协作：商品目录、订单运营、平台发布。涉及价格/账号/结算的实施按高风险业务契约验收，数据库与发布分别审批。

### 阶段一：确认分配与处理已知异常

- 按两个具体客户编号只读核对实际客户档案、retail/wholesale、员工/代客身份、类型变更记录及当时价格版本。
- 保留合法零售/批发差异；若同属已审核维修店却被分到零售，再按证据调整。REMAX 继续执行现有免折扣政策，不擅自启用15%优惠。
- 核对4个活跃人工等级冲突、1个价格倒挂、5个低毛利商品，形成精确修复清单、调整前后对比和补偿方案。
- 验收：CB25橙色在批发档 €1.40、零售档 €1.90；每个等级均不折扣，目录到订单保持一致。若老板决定统一价，作为新的商业政策单独执行。

### 阶段二：统一规则和报价链路

- 分开管理：登录身份、交易档案、价格类型、消费等级、人工覆盖、促销、商品价格政策、账期/授信。等级优惠不自动等同于信用授权。
- 建议基础等级取有效人工覆盖，否则消费等级；促销默认只提升、不降低基础权益，过期恢复基础等级。若需强制替换等级，使用明确政策字段，不靠隐含优先级。
- 当前固定减额先保持；拟改百分比时按品类、成本和销量模拟毛利后确定，不能全站直接套同一百分比。
- 商品免折扣改为稳定的政策标识，避免只靠品牌/分类文本决定；明确协议价、等级价、价格组是否叠加及优先级。
- 单一权威报价接口输入客户、SKU、数量、时点，返回基础价、实际优惠、最终价、原因、版本、到期时间。失败关闭交易报价；不返回猜测价。
- 列表、详情、购物车、预览、最终订单共用同一规则。下单事务最终校验库存/价格版本，变化时展示新旧差额让客户重新确认。
- 验收：两类价格 × 七等级 × 免折扣/普通商品；再覆盖人工与促销冲突、到期、数量门槛、协议价、价格组和毛利底线。

### 阶段三：可解释、可审计与持续发现异常

- 客户看自己的价格类型和有效等级；后台可以解释某个 SKU 为什么得到该价格，不向客户泄露成本或其他客户价格。
- 变更价格类型/等级/政策须记录操作人、原因、生效与结束时间、前后差异；批量修改先预览影响，不追溯改写已成交订单。
- 订单保留成交快照与定价版本，退款消费规则幂等化；付款、退款、撤销后按统一口径重算。
- 增加定期异常检查：人工/有效等级冲突、零售低于批发、低于批准底线、免折扣商品出现折扣、无有效报价版本、同一客户各页面价格不一致。这里只提出监控计划，未创建定时任务。
- 补真实场景集成测试和登录UI验收。现有源码字符串合同测试可保留，但不能替代数据库报价与下单行为测试。
- 修复完成后再按审批发布；观察价格服务失败率、价格变化拒单率与价差投诉，异常可按政策版本回退。降低复发概率不能承诺软件永远零错误。
